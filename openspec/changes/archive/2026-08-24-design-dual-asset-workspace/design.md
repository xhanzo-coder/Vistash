## Context

现有应用已实现图片入库、图片文件夹、标签、查询、色卡与图片回收站，但前端是功能验收骨架：单击会用整页详情替换网格，没有多选、真正界面虚拟化、备注、收藏或提示词工作台。`Catalog` 已是库权威元数据与 SQLite 派生索引的一致性入口，但 `catalog.rs` 已较大，不能把新提示词逻辑继续堆入单文件。

本设计来自一次逐项产品访谈与一手竞品调研。已确认的核心约束是：图片与提示词是两类独立素材，文件夹树分离，标签词表共享，两者只建立可选普通关联。第一版只完成两类素材管理，不实现反推、生图和 provider。调研详情保存于 `.research/Vistash前端产品与竞品调研.md`，该文件为本机调研记录，OpenSpec 中的规范条款才是实施事实来源。

## Goals / Non-Goals

**Goals:**

- 建立图片/提示词两个独立又可选关联的工作台，并使它们共用一致的导航、选择、搜索、检查器与危险操作语法。
- 为提示词素材、提示词文件夹、共享标签、备注、收藏、普通关联和提示词回收站定义人类可读、可迁移、可重建的权威格式。
- 让 10,000 条图片或大文本提示词查询的中央集合使用真正界面虚拟化，同时保留键盘、多选与滚动上下文。
- 实施前以可丢弃低保真原型验证信息架构、四种中央视图、检查器、批量操作和窄窗口状态。
- 用语义主题 token 隔离结构与视觉，允许第一版先验证浅色布局，不提前确定品牌色值。

**Non-Goals:**

- 不实现图片反推、生图、生成记录、provider/凭据、目标模型档案与自动来源识别。
- 不为普通关联增加生成/参考/反推类型，不根据文件名、导入时间或图像内容猜测关联。
- 不实现提示词版本历史、Markdown/富文本备注、星级/旗标/颜色评级、智能文件夹或通用撤销栈。
- 不在本变更中选定最终颜色、字体、品牌图形、具体多主题皮肤或动效风格。
- 不引入任意停靠面板系统、无限画布、网页抓取、浏览器扩展或通用文件管理器。

## Decisions

### 一、用双工作台而非混合流表达两类一等素材

顶栏提供图片素材与提示词两个一级入口；每个入口使用左分类、中央集合、右检查器的同一框架，但图片中央以画面为主，提示词中央以文本身份为主。单击只更新检查器，双击/`Enter` 才进入聚焦模式。

备选“一个混合图片/提示词瀑布流”被否决，因为两类素材的主要可读内容、分类树、批量操作与详情密度不同，混合流会迫使卡片变成无法承载两者的最小公倍。备选“提示词仅是图片字段”同样被否决，因为提示词可以不关联图片并拥有独立组织、收藏与搜索语义。

### 二、提示词使用稳定 ID 与单文件当前值

提示词权威文件存放于 `prompts/objects/<prompt-id>.json`，回收站文件存放于 `prompts/trash/<prompt-id>.json`。`prompt-id` 使用时间可排序的 UUIDv7，编辑不改变 ID。每个文件至少包含：格式版本、ID、当前正文、可选标题/模型/参数说明、纯文本备注、收藏、提示词文件夹、共享标签、有序关联图片哈希、可选封面哈希、创建/更新/删除时间与删除前文件夹。

提示词文件夹清单使用独立的 `prompt-folders.json`，不复用图片 `folders.json`。两套文件夹和全部标签均由使用者自定义，系统不预置题材、风格、模型或用途分类。标签词表不建立第三份权威文件：共享词表是图片侧车与提示词文件中用户已输入标签字面值的并集，派生索引按素材类型分别计数。

备选“正文内容哈希作为 ID”被否决，因为提示词是可编辑当前素材，编辑不应改变其收藏、文件夹或关联身份。备选“每次编辑创建新文件”被用户明确否决，第一版不保留版本历史。

### 三、普通关联的唯一权威方是提示词文件

每条提示词文件保存有序 `linked_image_hashes` 与可选 `cover_image_hash`。图片侧车不保存反向列表；SQLite 通过 `prompt_images(prompt_id, image_hash, ordinal)` 表提供从图片反查提示词。这使一次关联只需改动一份权威文件，避免两边列表双写后分叉。

图片移入回收站时不改提示词文件，图片索引的删除状态用于显示“关联图片已删除”。提示词移入回收站时文件连同关联一起移动，图片反查显示“关联提示词已删除”。图片永久 purge 前，`Catalog` 用元数据批量事务从所有正常/回收站提示词中移除该哈希并重选封面；任一提示词权威写入失败则该图片 purge 失败且图片对保持完整。提示词 purge 只删除其文件与索引关联，不写图片侧车。

备选“关联独立文件”被否决，因为封面、顺序与提示词检查器都需要完整关联集，独立文件会增加全库扫描与孤儿文件检查。备选“两侧侧车都写”被否决，因为它把一个关系变成两份权威事实。

### 四、库格式升级使用可恢复的一次性 v1 到 v2 迁移

`library.json` 升级到格式 v2 并新增稳定 `library_id`；图片侧车格式升级到 v2，强制写入纯文本 `note` 与布尔 `favorite`。开库发现 v1 时不以 serde 默认值猜测新字段，而是启动明确 `v1-to-v2` 迁移：

1. 获得独占迁移锁，建立持久化 journal 和原字节备份树。
2. 建立新 prompt 目录、`prompt-folders.json` 与 `library_id`，但暂不提升权威库版本。
3. 按 journal 记录逐个把 v1 图片侧车解析为显式 `AssetSidecarV1`，写成 v2；图片输入与派生缩略图不改。
4. 重建 v2 SQLite 索引并比较迁移前后图片核心快照。
5. 最后原子写入 v2 `library.json`，再删除 journal 与备份。

任一步返回失败时必须根据备份回复已处理权威文件并保留 v1 `library.json`。进程中断后下次开库必须读取 journal 继续或回滚，MUST NOT 把混合侧车当成正常库。迁移与文件夹大批量重命名一样在后台执行并通过 typed `Channel` 呈现已处理数、总数与当前文件。

备选“永久兼容两种侧车”被否决，因为它会在每次读取中保留遗留分支。备选“把备注/收藏放在叶目录外”被否决，因为单独取走图片叶目录将不再获得完整权威元数据。

### 五、在现有 Catalog 公开入口后拆分内部图片、提示词与关联模块

`Catalog` 继续是命令层唯一的库一致性入口，但内部拆分为图片元数据、提示词元数据、普通关联/封面、生命周期与派生查询模块。命令层只调用如下领域意图接口，不学习 JSON 路径或 SQL：

```text
Catalog::image_snapshot(ImageQuery)
Catalog::prompt_snapshot(PromptQuery)
Catalog::global_search(text)
Catalog::create/update_prompt(...)
Catalog::set_image_note/favorite(...)
Catalog::set_prompt_note/favorite/folders/tags(...)
Catalog::link/unlink_images_and_prompts(...)
Catalog::batch_*(...)
Catalog::delete/restore/purge_prompt(...)
```

SQLite 索引提升结构版本，新增 prompts、prompt_folders、prompt_tags 与 prompt_images，并为 images 增加 note/favorite 列。重建必须同时扫描正常与回收站图片侧车、正常与回收站提示词文件及两份文件夹清单。

备选“单独 PromptCatalog 由 Tauri 自行组合”被否决，因为图片 purge、全局搜索和跨库关联需要一个统一事务边界。备选“继续把全部逻辑放入 catalog.rs”被否决，因为它会进一步扩大已经超过两千行的文件，破坏 locality 与可导航性。

### 六、批量组织使用逐项失败隔离和统一 BatchReport

批量标签、文件夹、收藏与普通关联对每个目标执行完整单项权威写入与索引更新，一项失败不回滚先前成功项。返回值统一为 `BatchReport { succeeded, failures[{id, display_name, error}] }`，界面逐项显示失败。批量文件夹树重命名/删除仍使用已批准的 MetadataTransaction 全或无语义，因为它是一个跨文件逻辑操作，不是独立素材操作集合。

备选“所有选中素材作为一个全局事务”被否决，因为数千项中一个被占用文件会无谓丢弃全部已完成工作，也会要求巨大备份集。

### 七、前端用稳定选择模型与按需详情分层代替整页切换

React 内部建立统一 `SelectionModel`，保存查询有序 ID、活动 ID、选中 ID 集合、范围锚点和聚焦 ID。图片瀑布流/列表与提示词卡片/列表共用状态机与键盘语法，但渲染器各自优化。多选检查器只请求共同/混合组织摘要，单选检查器再按需请求原图、色卡、完整提示词、备注和关联。

不引入 Redux/Zustand：工作台状态使用 `useReducer` 与局部 Context 按库边界分割，服务端快照继续经集中 IPC 模块进入。只有后续出现跨窗口或多路由共享可编辑草稿时，才重新评估全局状态库。

提示词正文/标题/模型/参数使用显式编辑草稿和保存，备注使用独立自动保存草稿。未保存主要字段阻止丢失上下文；备注保存失败时草稿留在检查器。

### 八、虚拟化方案先由可丢弃原型决策

生产代码不在本设计中盲选一个瀑布流库。先用 10,000 条固定宽高数据和长提示词 fixture 建立可丢弃原型，比较候选依赖与小型自有定位器的：

- WebView2/React 19/TypeScript 7 兼容性与包体积。
- 瀑布流可变高度、列数变化、定位活动项与恢复滚动。
- Ctrl/Shift/框选、ARIA 复合网格焦点与移动後项存活。
- 10,000 项首屏、快速滚动、视图切换和窄窗口重排的 DOM 数、帧时间与内存。

原型仅回答布局/选择/性能问题，默认丢弃，MUST NOT 直接复制进生产目录。方案选定后把依赖、数据规模、实测门禁与拒绝方案补回本设计，并经用户验收低保真信息架构后才允许生产前端任务开始。

实测后选定 `@tanstack/react-virtual@3.14.10` 作为生产实现候选，生产锁定这一直接依赖版本；其解析到的 `@tanstack/virtual-core@3.17.8` 必须由 lockfile 固定。选择原因是它提供 headless API、可变高多 lane、稳定 `scrollToIndex`、快照/初始测量缓存，并明确接受 React 19。Vistash 自己持有选择、焦点、键盘、框选与 ARIA 语义，虚拟化依赖只负责位置和可见项，不得成为选择状态的权威方。

原型使用每库 10,000 项，在 Playwright Chromium、React 19.2.8 与 TypeScript 7.0.2 下完成实测。小型自有定位器与 TanStack 的首屏集合 DOM 分别为 21 与 22；45 次、每次 900 CSS px 的快速滚动平均双帧为 32.90 ms 与 32.88 ms，最慢双帧为 35.10 ms 与 35.20 ms；滚动后 JS heap 为 30.25 MiB 与 29.34 MiB。TanStack 详情切换为 42.94 ms，能定位第 0、4,999 与 9,999 项，10,000→1→10,000 过滤恢复正常，720/900/1,200/1,440 CSS px 重排均无水平溢出。原型同时通过 Ctrl/Shift/框选、方向键、`Ctrl+A`、`Ctrl+F`、`Ctrl+K`、`Escape` 和 125%/150%/200% device scale 验收。一次 64 ms 长任务发生在包含 Vite 开发服务和 fixture 初始化的全程观察中，因此生产门禁以 release WebView2 重测为准。

当前同时打包两个比较实现的原型产物为 248.66 kB、gzip 76.84 kB；已安装的 `react-virtual` 与 `virtual-core` 文件约 55.2 KiB 与 400.8 KiB（未压缩开发安装体积），不能当作生产增量包体。生产只保留 TanStack 适配器后，必须由构建分析记录真实 gzip 增量。TypeScript 严格检查与 Vite production build 已通过；WebView2 使用标准 ResizeObserver、transform 与滚动元素 API，不依赖 Chromium 私有接口，但仍需在 Windows Tauri release 壳完成最终兼容验收。

不选 `react-virtuoso` 组合：`VirtuosoGrid` 面向等尺寸网格，真瀑布流需要独立 `@virtuoso.dev/masonry`，后者公开 API 未提供本需求明确需要的定位与快照合同。不选 `masonic`：虽然瀑布流定位能力强，但依赖更多、数据缩短需要显式重置 positioner、没有快照，React 19/TypeScript 7 组合仍需额外兼容验证。不选小型自有定位器进入生产：当前原型每次滚动用 O(n) 过滤可见项，也不提供动态测量、锚点恢复、完整定位与长期可维护的无障碍接缝；它只保留为比较基线。

响应式断点按中央内容最小可用宽度确定：大于 1,080 CSS px 时平衡变体保留三栏；小于等于 1,080 CSS px 时左右栏默认收起并由边缘入口打开抽屉；小于等于 720 CSS px 时进一步压缩顶栏、工具条与详情列。用户手动调整的宽屏栏宽和分库视图写入本地布局偏好；窄屏自动收起不覆盖其宽屏宽度。生产不得按物理像素或系统缩放百分比另建分支。

产品所有者于 2026-08-20 明确验收通过 `A — 平衡工作台` 的低保真信息架构，包括双库一级入口、左分类、中央瀑布流/详情列表、右检查器、可选普通关联、纯文本提示词卡片和窄窗口抽屉。该验收不确认具体颜色、字体或品牌视觉。原型源码与实测产物作为主要来源留在 `prototype/dual-asset-workspace` 分支，生产实施只提取本设计记录的信息架构与门禁，禁止复制原型代码。

### 九、视觉层只确定语义 token 与信息层级

第一版建立表面、文本、边界、强调、选中、焦点、危险、间距、字号、阴影与动效的语义 token，以一套浅色占位取值验证对比度与组件状态。该占位值不得被文档描述为最终品牌设计；颜色、字体、图标和多主题变体由用户在后续视觉设计阶段决定。

备选“继续深化现有暖灰/深墨/朱红”被否决，因为该方案是功能验收阶段的临时选择，没有得到产品所有者的视觉确认。备选“直接写死一套浅色”也被否决，因为用户已要求后续支持多风格且由自己完成具体视觉设计。

## Risks / Trade-offs

- [库 v1→v2 迁移必须重写全部图片侧车，Windows 下可能耗时数分钟] → 迁移在后台执行、逐项呈现进度，用持久 journal/备份支持中断后恢复，并在 1,000/10,000 侧车 fixture 上测量。
- [提示词文件保存关联会使图片 purge 需要批量修改提示词] → 只在不可恢复 purge 时执行跨文件 MetadataTransaction；普通回收站删除不写提示词。
- [瀑布流虚拟化与复合键盘/框选交互容易相互破坏] → 先原型固定选择状态机和性能门禁，再决定依赖与生产实现。
- [四种中央视图与两套文件夹使界面状态显著增长] → 使用共享工作台状态机和按库隔离的查询/布局状态，避免在顶层组件堆叠布尔量。
- [共享标签词面可能产生同名、大小写或近义词混乱] → 本变更只保证同字面值共享与分库计数；标签重命名/合并属于后续独立需求。
- [无具体视觉定稿会让原型与生产样式有差异] → 原型只验证信息层级、密度、交互和响应式；生产组件坚持语义 token，视觉值可以后置替换。

## Migration Plan

1. 在可丢弃原型中确认信息架构、虚拟化方案、窄窗口断点与选择状态，将用户验收作为生产任务门禁。
2. 实现并测试 v1→v2 库迁移、PromptAsset/提示词文件夹、SQLite v2 重建与普通关联，暂不更换前端。
3. 增加新的集中 IPC/DTO，用 Tauri mock 锁定两库查询、批量结果、关联与布局偏好合同。
4. 以新工作台外壳替换当前巨型 `AssetWorkspace`，先保持现有图片能力等价，再依次打开多选、备注/收藏、提示词工作台和普通关联。
5. 在临时 E 盘库复制上执行 Windows release 迁移与端到端验收，不对使用者真实库首次运行未验证迁移。
6. 回滚应用二进制时，v2 库不允许被 v1 应用打开；迁移 journal 的备份只在成功后清理，并在用户明确退回前保留可回复点。
