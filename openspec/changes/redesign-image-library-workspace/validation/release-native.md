# Windows release 原生验收（11.5）

日期：2026-08-29。

## 已完成

- `pnpm tauri build --no-bundle` 在当前 Windows 主机通过，产物为 `app/target/release/vistash.exe`。
- release 构建启动后能读取隔离库、显示 v1→v2→v3 迁移流程并进入新版 `AppShell`。此前迁移前索引重建错误使用 v3 解析器的问题已修复，并以真实 `Index::rebuild_at` 回归测试锁定。
- `node app/scripts/e2e-release.mjs` 已在 release WebView2/CDP 上完整通过：真实 v1→v3 迁移、备注/收藏落盘、多选批量标签、图片文件夹组织、分库搜索、全局搜索、提示词关联与封面、图片/提示词回收站还原和清空均通过；脚本使用 v3 `folder`、`source.filename` 与 `deleted_from_folder` 权威字段断言。
- platform contract、浏览器验收和 Rust 测试覆盖文件/目录来源、位图/文本分流、对话框取消、默认程序打开错误码及租约释放。

## 尚需发布环境操作

上述脚本通过 CDP 驱动 release WebView2，但仍没有替代 Windows 桌面层的全部验收。11.5 还需要在真实窗口中逐项操作并记录证据：资源管理器 `CF_HDROP` 文件/目录拖放、文件列表剪贴板、截图位图剪贴板、文本输入框普通粘贴、原生图片/目录对话框、默认程序打开、原生标题栏以及 780px 窄窗口。由于这些动作依赖桌面和系统剪贴板，不能由 headless/CDP 脚本单独证明，故 11.5 保持未勾选。

## 2026-08-31 真实桌面收尾复验

- 使用 `native-ui-session.mjs` 把 release 应用指向隔离运行副本；真实 `%APPDATA%\com.vistash.app` 先原子改名备份，测试结束后已恢复，隔离目录已删除。停止阶段发现 WebView2 句柄延迟释放会让首次目录删除返回 `EPERM`，脚本已改为识别“原配置已经恢复”并对测试目录执行有界重试，避免重复停止误触真实配置。
- 真实 Windows 图片文件选择器显示“选择要导入并关联的图片”，目录选择器显示“选择要导入的图片文件夹”；均以取消结束，当前库和选择保持不变。
- 真实 release 窗口调用“用默认程序打开”后，Windows Photos 打开所选测试图片；返回 Vistash 后出现“已交给 Windows 默认程序打开”反馈。
- 自定义标题栏按钮完成最大化/还原；双击标题栏空白区进入最大化，窄窗口缩放至 753×802 后切换为紧凑导航且无横向溢出。随后以 `Win+Right` 把 Vistash 贴靠到 1920×1080 屏幕右半区，窗口截图边界为 `originX=960, width=960, height=1032`。
- 窄窗口图片检查器能够进入“图片 × 提示词关联”，冻结 1 张目标图片、搜索已有提示词并切换到“新建提示词”；正文仍明确要求人工填写，没有出现 v0.1.0 不提供的反推入口。提示词页同尺寸复验中，2 张关联图片以“主预览 + 缩略图列表 + 打开当前图片”呈现，图片与提示词交互语言一致。
- 用户在前序逐轮评审中明确接受“图片页可创建提示词”和“提示词点击后展示多张图片”的方案，并在整体修改总结后授权实施；结合本次真实 release 同尺寸复验，12.5 完成。为保护测试基线中可能包含的个人图片，真实桌面截图不进入仓库；可重复视觉证据继续使用匿名 fixture 的 `app/artifacts/association-workflow/`。
- `computer-use` 对资源管理器与 Vistash 左右贴靠后执行了跨窗口指针拖动，但自动化输入没有产生可由目标窗口读取的 Explorer OLE 文件载荷；文件数保持 6。该结果既不能证明产品通过，也不足以判定产品失败，因此 11.5 仍只保留“使用真实鼠标从资源管理器拖入一个图片文件夹”这一项人工确认，不冒充完成。文件列表剪贴板、截图位图、文本粘贴、原生对话框、默认程序、标题栏、贴靠和窄窗口均已有真实证据。
