## 背景

本变更是 Vistash 的第一份生产代码。仓库此前只有归档变更 `2026-08-17-bootstrap-vistash-development-workflow` 与 `2026-08-18-establish-vistash-product-architecture` 产出的文档，五份主规格共 21 条需求已生效但从未被代码检验；没有 `package.json`，没有 `src-tauri`，没有任何可执行入口。

前一变更的第十八条决策把交付顺序改为"先框架、后反推"，本变更是该顺序下的第一步。它的定位不是把 v1 素材管理做完，而是打通一条贯穿全部架构层的最窄纵向切片：使用者选库 → 拖入文件夹 → 素材入库 → 网格出缩略图 → 点开看原图与色卡。文件夹、标签、搜索、删除界面与提示词库功能移到紧接的后继变更，理由见 `proposal.md`。

本设计一并承担 `codebase-design` 的职责：定义模块边界、依赖方向与测试接缝。这些内容在实施前必须确定，因为已生效需求中有四条（色卡确定性、导入回滚不变量、索引可重建、媒体处理归属 Rust 侧）只有在模块边界正确时才可被测试验证。

## 目标与非目标

**目标：**

- 建立 Tauri 2 工程结构，并使 lint、类型检查与测试三条命令首次真实可执行。
- 打通选库、导入、缩略图网格、单图预览与色卡这条纵向切片。
- 使四条最容易静默失败的承诺具备自动化测试：色卡确定性、哈希与寻址正确性、导入回滚不变量、索引重建等价性。
- 定义模块依赖方向，使核心领域逻辑不依赖 `tauri` crate，从而可在 `cargo test` 中直接验证。
- 解除前一变更的待确定问题六。

**非目标：**

- 本次不实现文件夹、标签、搜索、删除界面与提示词库功能。
- 本次不做界面精修、动效与主题；视觉设计留给 `frontend-design`。
- 本次不做打包、签名、自动更新与 CI。这些留给后续变更，因为它们需要先有可通过的本地命令。
- 本次不做虚拟滚动、文件系统监控与多格式专用预览；`asset-library` 现有需求已把它们排除在 v1 之外。
- 本次不承诺跨平台一致性，只承诺 Windows 上同一构建内的确定性，理由见第三条。

## 技术决策

### 一、领域逻辑与 Tauri 层拆为两个 crate，核心 crate 不依赖 `tauri`

应用源码位于 `app/`（布局理由见第十条），Rust 侧拆为两个 crate：

- `app/crates/vistash-core/`：领域逻辑，**依赖表中没有 `tauri`**。
- `app/src-tauri/`：Tauri 应用，依赖 `vistash-core`。

核心 crate 内部划分为以下模块，依赖只允许从左向右：

```
commands  →  import, index  →  library, hashing, sidecar, media, colorcard
```

- `library`：库骨架创建、库级元数据读写、格式版本校验。
- `hashing`：SHA-256 计算与两级 fanout 路径推导。
- `sidecar`：素材元数据侧车的序列化与反序列化。
- `media`：解码、降采样、缩略图编码。
- `colorcard`：OKLab 转换与确定性聚类，输入是 `media` 产出的像素缓冲，本身不接触文件系统。
- `import`：导入管线，编排上述模块并实现单素材回滚。
- `index`：SQLite 索引读写与从元数据文件重建。
其中 `commands` 属于 `app/src-tauri/`，是 Tauri 命令薄层，只做参数转换与错误码映射，不含业务判断。

拆成两个 crate 而不是靠约定，是为了让这条约束成为编译期事实：`vistash-core` 的 `Cargo.toml` 里没有 `tauri`，任何人想在核心逻辑里调用 Tauri API 都必须先改依赖表，而依赖表的改动在评审中看得见。若只用单 crate 加约定，`use tauri::` 混入核心模块不会有任何报错。理由不是分层洁癖：色卡确定性测试要跑上百次同一输入，导入回滚测试要注入写入失败，索引重建测试要构造完整库目录——这三类测试若需要启动 WebView 就会慢到不会被真正执行，而它们恰好是本次唯一能证明四条已生效需求成立的手段。

前端对应地划分为 `app/src/features/library`（选库与库状态）、`app/src/features/assets`（网格与预览）、`app/src/shared`（IPC 封装与错误码呈现）。IPC 调用 MUST 集中在 `app/src/shared`，不散落在组件里，使错误码到可读文案的映射只有一处。

### 二、SQLite 索引的版本不匹配即整库重建，不写迁移脚本

索引是纯派生数据，其唯一权威来源是库目录内的元数据文件。因此索引结构变更时的策略是：读取 `user_version`，与当前程序期望值不符即删除索引文件并全量重扫重建。

备选"为索引写增量迁移脚本"不采用的原因是成本与风险都更高而收益为零：重建成本等于一次目录扫描（当前 6 个素材，十万级素材下也是分钟级的一次性操作），而迁移脚本需要为每个版本对编写并测试，且一旦写错会污染索引却不被发现——正因为索引可重建，写错迁移的代价反而比不写迁移更大。

这条决策同时给出一个免费的诊断手段：任何"索引与磁盘不一致"的疑虑都可以用删除索引重建来排除。

### 三、色卡的确定性来自算法本身，不来自固定随机种子

K-means 需要初始质心。备选"k-means++ 配固定种子的 PRNG"不采用的原因是它把确定性寄托在 PRNG 实现上，而 Rust 生态的 PRNG 不保证跨 crate 版本产生相同序列，一次依赖升级就可能静默改变全库色卡结果。

采用完全确定性的初始化：把降采样后的有效像素按 OKLab 亮度排序，在其分位点上取 k 个初始质心。该过程只依赖输入数据，没有任何随机来源。排序需要稳定的全序，因此当亮度相同时按 `(a, b)` 通道再排序，最后按像素索引兜底。

其余确定性来源逐项固定：降采样长边固定、重采样滤波器写死为一个具体选择、聚类迭代次数与收敛阈值写死、小簇过滤、簇合并与强调色发现的阈值写死。内部计算用 `f64`，输出全部量化——十六进制值、三位小数的占比、四位小数的 OKLab 坐标，使浮点尾数噪声不进入侧车。

**输出的颜色取簇内 medoid，不取质心。**这是 `reverse-prompt` 已生效需求的硬约束而非本设计的选择：质心是簇内颜色的均值，在自然图像上几乎必然是一个原图里不存在的颜色，而色卡的用途之一是让使用者复制色号去用。因此每个簇的代表色取簇内距质心最近的真实采样像素，其 `hex` 直接由该像素的 RGB 得出。medoid 的决胜规则同样需要确定：距离相等时按 OKLab 全序、再按样本下标兜底。

**小簇过滤与强调色发现的先后顺序也是需求约束的。**过滤必须后行：强调色的占比通常低于过滤阈值，先过滤就会把它删掉。被过滤的簇其像素并入距离最近的保留簇而不是丢弃，否则占比之和会小于一，与"占比在有效像素内归一且总和为一"冲突。

**确定性承诺的边界必须说清**：承诺的是同一平台、同一构建下同一输入产出同一结果。跨平台或跨编译器版本的浮点行为差异不在承诺范围内。这个边界足以支撑已生效需求的意图——它要防的是"同一台机器上重算色卡结果漂移"，而不是跨机器复现。

### 四、缩略图存放于独立目录树，取 WebP 与长边 512

具体取值如下，其行为约束已写入 `asset-library` 的缩略图契约需求：

```
thumbnails/3f/a9/3fa9c2…e1.webp      与 objects/ 相同的两级 fanout，独立成树
```

- **独立成树**而非与本体同目录：本体目录是权威数据，缩略图是可重算的派生数据。混在一起会使"重建缩略图"这一常规操作向权威树写入，一次写入失败便与素材本体的完整性问题纠缠不清。
- **WebP**：素材可以是带透明区域的 PNG，JPEG 无透明通道会显示为不存在的实色背景；PNG 体积在缩略图规模下偏大；WebP 同时具备透明与体积优势，且 Windows 的 WebView2 原生支持。
- **长边 512、保持宽高比、不放大**：网格卡片在 2 倍 DPI 下的实际像素需求约 400，512 留出余量。不裁剪为方形的原因是画幅是素材的关键属性，方形裁切会使使用者在网格里对画幅产生误判。
- **有损编码，质量固定为 80**（任务 6.4 实测后确定，解除待确定问题二）。

**有损这一条是被实测纠正过来的，记录经过。**本变更的第一版实现用了无损 WebP，原因是 `image` 0.25 的 WebP 编码器只能无损——该 crate 自己的注释写着"If you need **lossy** encoding, you'll have to use `libwebp`"。这个限制当时没有被记录，于是"取一个保守的质量值"这句设计意图在实现里静默变成了"没有质量值"。

任务 6.4 在两张真实素材上实测，暴露了后果：

| 素材 | 原图 | 无损 512 缩略图 | 有损 q=80 |
| --- | --- | --- | --- |
| 941×1672 PNG | 2015 KB | 189 KB | 17 KB |
| 1179×1763 JPEG | 152 KB | **168 KB（比原图还大）** | 18 KB |

无损 WebP 在照片类内容上没有任何体积优势。第二行是判据：缩略图的存在意义是让网格加载比读原图快，而它比原图还大就把这个意义整个抵消掉了——100 张的网格要过 16 MB 的 IPC。

质量取 80 而非更高：实测 q=85 与 q=90 分别比 q=80 多花约 25% 与 60% 的体积。取 80 是保守值，且缩略图可全库重算，日后调整的代价是一次重建而不是格式迁移。**"512 长边在真实卡片尺寸下是否够清晰"这半个问题本次答不了**，理由见待确定问题一。

**透明通道不受有损编码影响。**libwebp 对 alpha 平面单独做无损压缩；实测 q=75 与 q=90 下全透明与全不透明区域的 alpha 值都精确保留。因此 `asset-library` 那条"缩略图编码格式必须支持透明通道"的需求仍然成立，无需修改。

**缩略图树带格式版本，不匹配即整棵清空。**编码器、质量参数或长边任一改动都必须提升 `import::THUMBNAIL_FORMAT_VERSION`，该版本号记在 `thumbnails/.format` 里，打开库时校验，不匹配即清空整棵树待按需重算。没有这个机制，改完参数后既有缩略图文件仍然存在，`ensure_thumbnail` 会认为它们没缺失而继续读回旧格式的字节，同一个库里混着两代缩略图且不报任何错——本次从无损切到有损时就会真的发生。清空是安全的：规格明确写了"缩略图全部缺失必须触发重新生成，禁止被报告为库损坏"。

**引入 libwebp 与第八条的关系必须说清。**第八条排除 AVIF 与 HEIC 的理由是"不把引入一个 C 库的成本压进第一个变更"，而这里恰恰引入了 libwebp（经 `webp` 0.3 与 `libwebp-sys` 0.9）。两者不矛盾，但需要说明区别：

1. **必要性不同。**AVIF 与 HEIC 是**扩大格式覆盖面**，属新增范围；libwebp 是让一个**已经决定的格式真正达到它的目的**——不引入，缩略图契约的意图就不成立。
2. **实测成本远低于当初的估计。**`libwebp-sys` 自带 C 源码，在本机 Windows MSVC 工具链下从源码编译耗时 9 秒，不需要任何系统级预装库；而构建前置条件里本来就要求 MSVC 生成工具。第八条的担忧是"引入一个 C 库的成本"，这项成本在本例中经实测被证明很小。

若日后重新评估 AVIF 与 HEIC，第八条的这条理由应按上述实测重新称量，而不是原样沿用。

### 五、导入本次全部串行，并留下可测量的优化基线

备选"解码与色卡计算并行"不采用的原因是它会使单素材回滚的不变量更难验证，而当前没有任何证据表明串行不够——库中仅 6 个素材。

但"没有证据"不等于"不会成为问题"，因此本次留下测量点：任务清单包含一条"记录导入 100 张素材的耗时并写入设计"，使后续是否并行化有实测依据而不是凭感觉。并行化只改执行器，不改任何契约。

### 六、前端不引入状态管理库

本次的前端状态只有三块：当前库路径、素材列表、选中项。引入 Redux 或 Zustand 会在只有三块状态时先付抽象成本，而 React 自带的 `useState` 与一个 context 已经足够。状态块数增长到需要跨路由共享与派生缓存时再引入，届时是增量替换而非重写。

### 七、提示词库定为一级导航入口（解除待确定问题六）

前一变更的待确定问题六在"与素材并列的一级导航"与"素材详情的侧栏"之间未决。本次定为一级入口。

理由是结构性的而非偏好：`prompt-library` 的已生效需求要求"手写录入的记录允许不关联任何素材"，而素材详情侧栏只能在选中某个素材时存在，结构上无法容纳这类记录。侧栏方案要成立就必须削弱那条需求。

本次该入口只呈现"尚未实现"。位置先定死的原因是导航层级是后续所有视图的容器，日后从侧栏改为一级入口会牵动整个布局。

### 八、本次支持的图片格式清单收窄为五种

支持 PNG、JPEG、WebP、GIF（取首帧）、BMP。排除 PSD、RAW、AVIF、HEIC。

排除依据分两类：PSD 与 RAW 已被 `asset-library` 的 v1 范围需求显式排除；AVIF 与 HEIC 排除的原因是其解码在 Rust 生态中通常需要额外的系统级依赖，会把"引入一个 C 库"的成本压进第一个变更。不在清单内的文件按 `import.unsupported_media_type` 拒绝，而不是尝试解码后失败——显式拒绝给出的错误信息更有用。

### 九、首批测试对应四条最易静默失败的承诺

测试不按代码覆盖率组织，而按"哪条承诺会在无人察觉时失效"组织：

1. **色卡确定性**：同一素材连续计算多次，结果逐字段相同。这条对应第十一条决策明令禁止的漂移。
2. **哈希与寻址**：已知内容映射到已知 SHA-256 与已知路径。这条防的是 fanout 切片位置写错——写错后库仍能工作，但两代路径不兼容。
3. **导入回滚不变量**：在复制成功后、侧车写入前注入失败，断言库中既不存在无侧车的本体也不存在无本体的侧车。这条对应 `asset-library` 的回滚需求，而该需求描述的失败模式在正常路径上永远不会出现，只能靠注入触发。
4. **索引重建等价性**：导入若干素材后取索引快照，删除索引文件重建，比对快照相等（已接受的不可重建字段除外）。这条对应"库格式开放且索引可重建"这项本项目最核心的承诺。

四项全部不需要 WebView，跑在 `cargo test` 中。

### 十、应用源码收进 `app/` 子目录，核心 crate 提为 `src-tauri` 的同级

仓库根只保留治理与参考材料，全部工程文件收进 `app/`：

```
05. Vistash/
  AGENTS.md  CLAUDE.md            共用规范
  openspec/                       规格与变更
  docs/research/                  调研材料
  app/
    Cargo.toml                    workspace 根，成员为 crates/vistash-core 与 src-tauri
    crates/vistash-core/          领域逻辑，依赖表中无 tauri
    src-tauri/                    Tauri 应用与 commands 薄层
    src/                          React 前端
    package.json  vite.config.ts  index.html
```

采用理由：仓库根同时承载 OpenSpec 治理文档、调研材料与三套 Agent 配置，把工程文件并入会使根目录成为杂物抽屉；而 `node_modules/` 与 `target/` 体量巨大，与 `openspec/` 平级会持续干扰浏览与检索。收进 `app/` 后，根目录的每一项都是人要读的东西。

**核心 crate 是 `src-tauri/` 的同级，不嵌入 `src-tauri/crates/`。** 这一条不可让步：`vistash-core` 的定义性质就是不依赖 Tauri，把它放进 `src-tauri/` 目录会在视觉上传达相反的信号；而它的 `Cargo.toml` 依赖表是第一条那项约束的唯一编译期检查，必须处在显眼位置。

备选**应用源码置于仓库根**（`create-tauri-app` 的默认产物形态）不采用。需要如实记录它被放弃的两项优点：一是与 Tauri 官方文档、CLI 默认值以及社区答案完全一致，偏离意味着此后每份 Tauri 资料的路径都要在脑子里换算一次；二是 `openspec/` 与源码同级，而这两者在实施期共变最紧——每完成一项任务都要同时改 `tasks.md` 与源码，收进子目录相当于在共变最紧的两者之间加了一层。

备选**嵌入 `src-tauri/crates/`** 不采用，理由同上一段的加粗部分。

备选 **`apps/vistash/` 加 `packages/` 的 monorepo 形态**不采用：当前只有一个交付物，`apps/` 与 `packages/` 各只有一个和零个成员，是 monorepo 的形态而没有 monorepo 的理由。

**接受的代价与缓解办法。** OpenSpec CLI 按当前工作目录解析 `openspec/`，因此实施期存在两个工作目录：OpenSpec 命令在仓库根运行，`pnpm` 与 `cargo` 命令在 `app/` 运行。这不是靠记性能绕过的问题——本次变更的实施过程中已经因为切换目录后运行 `openspec status` 而得到 `No changes exist` 的误导性报错。缓解办法是 `AGENTS.md` 必须显式列出两个工作目录及其各自的命令清单，使这项区分成为写下来的规范而不是口头默契。

**迁移触发条件：**出现第二个交付物（例如批量反推的命令行工具，或需要独立发布的共享 crate）时，把 `app/` 提升为 `apps/vistash/` 并新建 `packages/`。在那之前不预建这两层。

### 十一、前端 lint 采用 oxlint 与 tsgolint，不采用 typescript-eslint

本条是实施中被实测逼出来的，不是偏好。实测事实：

- 本项目使用 TypeScript 7.0.2。`typescript-eslint` 的最新稳定版 8.67.0 在加载时即拒绝运行，报错原文为 `typescript-eslint does not support TS 7.0`，其官方追踪 issue 的支持目标是 TypeScript 7.1 以上，而 7.1 在 npm 上只有 `-dev` 构建，没有稳定版。
- `oxlint` 1.79.0 配 `oxlint-tsgolint` 7.0.2001 的类型感知 lint 由 typescript-go 驱动，官方文档写明 **TypeScript 7.0+ is required**，实现了 typescript-eslint 全部 61 条类型感知规则中的 59 条，且规则选项与 typescript-eslint 等价。
- `react/rules-of-hooks`（0.3.3 起）与 `react/exhaustive-deps`（0.12.0 起）覆盖了原先由 `eslint-plugin-react-hooks` 承担的两条关键规则。

采用它的理由是这是唯一一个各组件互相支持的组合：TS 7 的原生编译器与 tsgolint 出自同一套 typescript-go。

备选**把 TypeScript 降到 6.0.3 以迁就 typescript-eslint**不采用：那等于为了迁就一个正在这条轴上被取代的 linter，把编译器往回退一个大版本。需要如实记录它被放弃的优点：typescript-eslint 生态成熟、第三方规则插件远多于 oxlint，规则覆盖也没有"缺 2 条"这种未点名的空白。

备选**保留 TypeScript 7 但放弃前端 lint**不采用：ESLint 的默认解析器读不了 `.tsx` 语法，`pnpm lint` 会退化成一条什么都不检查却始终通过的命令，而 `AGENTS.md` 的门禁要求三条命令是真实的。一条永远通过的门禁比没有门禁更坏，因为它会被当成证据。

**接受的代价。** oxlint 的类型感知模式官方措辞是仍在成熟，保留意见有三条：规则覆盖不完整（官方称"非常接近"）、超大代码库可能内存占用偏高、性能仍在改进。当前前端只有两个文件，三条都未构成实际约束；其中内存那条需在前端规模显著增长后复查。缺的那 2 条规则官方未点名，因此无法评估它们是否命中本项目关心的风险。

`react/react-in-jsx-scope` 必须在配置中显式关闭：自动 JSX 运行时下该规则是误报，而 oxlint 尚无 JSX 运行时设置项。`eslint-plugin-react` 的 `jsx-runtime` 预设同样关闭它，因此这不是本项目的特殊处理。

选定的规则集不追求覆盖面，而是对准一个具体风险：IPC 边界上的类型谎言。`invoke` 的返回值在类型系统里是 `unknown`，一旦被断言成某个类型就不再受任何检查，因此 `typescript/no-unsafe-*` 七条与 `no-explicit-any` 全部设为 error。

**为何不新建 OpenSpec 变更。** `AGENTS.md` 要求更换运行时技术栈必须走新变更，而其点名的运行时技术栈是 Tauri 2、React/TypeScript、Rust 与 SQLite。lint 工具不在其中，也不进入运行时产物，因此按本变更的实施决策记录处理。

**迁移触发条件：**`typescript-eslint` 发布支持 TypeScript 7 的稳定版，且届时 oxlint 的类型感知覆盖仍不完整时，重新评估这一条。

## 风险与权衡

- **风险：Tauri 2 在 Windows 上依赖 WebView2 运行时。** → Windows 11 自带 WebView2，本机满足开发需要。分发时的引导安装留到打包变更处理，不影响本次。
- **风险：`f64` 浮点计算的确定性在跨平台时不成立。** → 已在第三条明确承诺边界为同平台同构建，并说明该边界足以覆盖需求意图。
- **风险：缩略图长边 512 在 4K 素材配大卡片时可能偏软。** → 缩略图是派生数据，可全库重算，调整该值的代价是一次重建而非格式迁移。列入待确定问题待实测。
- **风险：串行导入在导入数百张时可能明显偏慢。** → 已在第五条留下测量点；并行化不触碰契约。
- **风险：色卡的阈值参数（小簇过滤、邻近合并、强调色发现）本次只能凭经验取值。** → 参数写死并纳入 `algo_version`；调参即提升版本号并触发全库重算，不会出现同库内两种参数的结果混存。
- **风险：两个工作目录导致命令在错误目录下执行。** → 第十条已记录该代价并要求 `AGENTS.md` 显式列出两个目录的命令清单；本次实施中已实际发生过一次，因此这不是假想风险。
- **风险：oxlint 的类型感知 lint 仍在成熟期。** → 已在第十一条记录官方的三条保留意见与当前不构成约束的理由，并给出复查触发条件。缺失的 2 条规则无法点名，因此 `code-review` 仍是类型边界问题的第二道检查，不把 lint 当作唯一证据。
- **风险：本次跳过 `frontend-design` 直接实现界面，可能产生需要重做的布局。** → 本次刻意只做无样式取舍的骨架：网格、预览、导航三块，不做视觉决策。真正的视觉设计在后继变更由 `frontend-design` 处理，届时替换的是样式层而非结构。

## 迁移与实施步骤

1. 初始化 Tauri 2 工程与前端骨架，落地 lint、类型检查与测试三条命令。

5. 实现 `commands` 薄层与前端选库、网格、预览三块视图。

7. 运行严格校验与 `code-review`，归档本变更。

回滚方式：本变更是仓库第一份生产代码，回滚即移除新增工程目录与本变更目录，不影响任何既有能力。库格式自本次起对外承诺，因此若已产生真实库数据，回滚不得删除使用者的库目录。
